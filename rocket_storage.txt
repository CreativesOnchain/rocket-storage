Rocket Pool RocketStorage Upgrade Effects Gate
Overview
Build a standalone, open-source CLI that deterministically replays a Rocket Pool protocol upgrade and verifies whether the transaction produced exactly the declared RocketStorage changes.
The first supported case will be the executed Rocket Pool v1.4 / Saturn 1 mainnet upgrade. The tool will compare the observed upgrade effects against a reviewed, source-anchored expected-effects manifest and produce a reproducible PASS, FAIL, or UNKNOWN attestation.
Problem being solved
Existing Rocket Pool verification work confirms that the published source, bytecode, contract addresses, and deployed implementations match. However, it does not fully answer:
Did the upgrade transaction make every expected typed RocketStorage change—and no undeclared change?
RocketStorage uses opaque bytes32 keys and generic typed functions such as setUint, setAddress, setBool, and corresponding delete operations. A normal trace therefore shows raw keys and values without explaining their Rocket Pool meaning.
This tool adds the missing semantic layer.
Core workflow
The CLI will:
Pin the execution environment
Chain ID
Pre-upgrade block number and block hash
Upgrade transaction or calldata
Upgrade contract
RocketStorage address
Rocket Pool source commit
Foundry/Anvil and tool versions
Replay the exact upgrade
Fork Ethereum from the pinned pre-upgrade state.
Replay the real Saturn 1 upgrade transaction using Foundry/Anvil or another deterministic EVM runner.
Capture RocketStorage effects
Record all calls to typed RocketStorage mutators:
setAddress, setBool, setBytes, setBytes32
setInt, setString, setUint
corresponding delete functions
addUint and subUint
Record caller, selector, raw key, type, old value, new value, and execution order.
Decode effects into semantic paths
Convert raw keys into readable meanings such as:
protocol settings;
contract name-to-address registrations;
contract.exists flags;
permissions;
deleted settings;
protocol version values.
Validate external calls
Check declared initializer and other outbound calls by:
target;
function selector;
ETH value;
expected multiplicity.
Compare expected versus observed effects
Every observed mutation must map to exactly one manifest entry.
Every required manifest entry must be observed with the correct type, old value, new value, and multiplicity.
Unknown keys and unsupported call shapes must fail closed.
Generate a deterministic proof bundle
Machine-readable JSON attestation
Reviewer-readable Markdown report
Normalized observed trace
Manifest lock file and hashes
Stable exit codes for CI
Result meanings
PASS: All required RocketStorage effects and allowed external calls match the reviewed manifest exactly.
FAIL: A known requirement is violated—for example, a wrong value, missing deletion, swapped address, duplicate write, or unexpected initializer.
UNKNOWN: The tool encounters an undecoded key, unsupported call form, incomplete trace, or another condition it cannot safely interpret.
Both FAIL and UNKNOWN return a non-zero exit code.
A PASS means only that the replayed payload conforms to the reviewed manifest within the documented observation boundary. It must not be described as an audit, security certificate, or proof that the entire upgrade is safe.
Manifest trust model
The expected-effects manifest must be derived from the pinned upgrade source, applicable RPIPs, and other ratified materials.
To prevent the manifest from simply copying the observed trace:
the expected manifest should be authored from the source and specifications;
it should be committed and hash-locked before final reconciliation with the normalized observed trace;
a second contributor must review it independently;
each entry must include its semantic path, type, expected old/new value, source anchor, requirement level, rationale, and expected multiplicity;
the proof bundle must include the manifest hash and review-record hash.

The normalized semantic output must be hash-stable across repeated runs. Wall-clock timestamps should either be excluded from the normalized artifact or stored only in a clearly excluded metadata section.
Explicit non-goals
The MVP will not:
build a new EVM or fork engine;
replace Foundry or Anvil;
perform source or bytecode verification;
claim universal coverage of storage changes inside every external contract;
automatically infer governance intent from natural-language RPIPs;
provide a dashboard, hosted service, wallet, or governance UI;
integrate into Smartnode;
automatically support Saturn 2 before its payload is stable;
claim that PASS means the upgrade is audited or secure.

Brief MVP / To-Do Plan
1. Feasibility spike
Before the full implementation:
replay the pinned Saturn 1 transaction;
capture at least one real setUint call;
capture at least one contract-registration mutation;
create a small source-derived manifest;
generate one PASS result;
introduce one undeclared write or wrong value and confirm non-zero FAIL/UNKNOWN;
run twice and confirm identical normalized hashes.
2. Repository and replay foundation
Create the CLI repository and basic command structure.
Pin Foundry/Anvil and all dependencies.
Validate chain ID, block hash, transaction hash, source commit, upgrade contract, and RocketStorage address before execution.
Add the archive-RPC integration command.
Save frozen normalized fixtures for offline testing.
3. RocketStorage mutation capture
Instrument the replay to capture all supported typed mutator calls.
Read the correct typed value before and after each mutation.
Preserve deterministic call order.
Normalize addresses, integers, byte strings, and encoded values.
Fail if the trace is incomplete or comes from an unexpected RocketStorage address.
4. Semantic manifest and review process
Define the YAML or JSON manifest schema.
Build the complete v1.4 semantic key catalogue.
Add source/RPIP anchors and expected old/new values.
Add required/optional status and multiplicity.
Define the external-call allowlist.
Hash-lock and independently review the manifest before final trace reconciliation.
5. Comparator and verdict engine
Implement checks for:
missing required effects;
undeclared writes;
wrong values;
incorrect types;
duplicate mutations;
omitted deletions;
swapped contract addresses;
unexpected external calls;
wrong target, selector, value, or multiplicity;
unresolved keys and unsupported call forms.
Return deterministic PASS, FAIL, or UNKNOWN with specific machine-readable reasons.
6. Golden fixture and adversarial tests
Create the full Saturn 1 golden fixture and at least these corruption tests:
undeclared RocketStorage write;
wrong expected uint;
missing required deletion;
swapped implementation address;
unexpected initializer;
duplicate semantic mutation;
type drift for a known key;
incorrect external-call selector;
incorrect external-call multiplicity;
wrong chain or block hash;
reordered manifest producing the same normalized hash.
7. Proof bundle, CI, and release
Generate JSON and Markdown attestations.
Bind outputs to all transaction, source, manifest, runtime, and review hashes.
Add offline unit and golden tests.
Add an optional live archive-RPC integration test.
Run the complete offline suite in CI.
Add a clean Linux/container entry command.
Document the trust model, observation boundary, manifest-authoring process, result meanings, and non-goals.
Tag the first reproducible release.
MVP completion condition
The MVP is complete only when a reviewer can clone the repository, run one documented command, reproduce the v1.4 attestation, receive PASS for the locked golden fixture, receive non-zero results for every corrupted fixture, and obtain the same normalized output hash across repeated runs.
